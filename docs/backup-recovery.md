# Backup, recovery and rollback

Operational runbook for the Kailo CMS (`cms`, Strapi 5 on PostgreSQL)
and the storefront (`frontend`, TanStack Start on Nitro, in a container).

Everything here was written against PostgreSQL 17.10 and **the dump/restore
cycle in [Restoring](#restoring) was executed end to end** — see
[Proof it works](#proof-it-works).

---

## What actually needs backing up

There are three pieces of durable state, and they fail differently.

| State | Where it lives | Backed up by |
|---|---|---|
| **Content + admin users + permissions** | PostgreSQL | `pg_dump` — [below](#the-database) |
| **Uploaded media** | `public/uploads` on the local provider, or the bucket once S3/Cloudinary is on | [Uploaded media](#uploaded-media) |
| **Code + the committed CMS snapshot** | git | git, plus the tagged container images |

The storefront itself holds nothing: in snapshot mode it is a pure function of
the repo, so "restoring the frontend" means redeploying a commit.

> **The snapshot is not a backup.** `frontend/src/lib/cms-snapshot/` is a
> point-in-time copy of the seeded content, regenerated by hand with
> `node scripts/snapshot-cms.mjs`. It rescues the *storefront* if the CMS is
> down, and it holds no admin users, no permissions, no form submissions and no
> cart rows. It is a fallback, not a restore path.

## The database

### Taking a dump

Custom format (`-Fc`) — compressed, and it is what `pg_restore` needs for
selective restores and parallelism:

```bash
pg_dump -h "$DATABASE_HOST" -p "$DATABASE_PORT" -U "$DATABASE_USERNAME" \
        -d "$DATABASE_NAME" -Fc -f "kailo-$(date +%Y%m%d-%H%M%S).dump"
```

Hosted Postgres hands you a single connection string instead:

```bash
pg_dump "$DATABASE_URL" -Fc -f "kailo-$(date +%Y%m%d-%H%M%S).dump"
```

Put the password in `~/.pgpass` (mode `600`) or `PGPASSWORD`, never on the
command line — an argument is visible to every other process on the box.

The current dump is **~0.33 MB**, because media lives on disk rather than in the
database. It stays small; the schedule below is cheap to run often.

### Schedule

Nightly full dump, 30 days retained, is the right default for a site whose
content changes on an editor's timescale. As a cron entry:

```cron
# 03:15 daily — dump, then drop anything older than 30 days
15 3 * * * pg_dump "$DATABASE_URL" -Fc \
  -f /var/backups/kailo/kailo-$(date +\%Y\%m\%d).dump \
  && find /var/backups/kailo -name 'kailo-*.dump' -mtime +30 -delete
```

Three things that decide whether this is a real backup or a comforting file:

1. **Copy it off the machine.** A dump on the same disk as the database is not
   a backup of that disk. Ship it to object storage (`aws s3 cp`, `rclone`) on
   the same schedule.
2. **Take one before every deploy that changes the content model** — a schema
   change or a `SEED_VERSION` bump. Those are the migrations you might need to
   walk back, and Strapi applies schema changes on boot.
3. **Alert on absence, not just failure.** A cron that stops firing is silent.
   Check the newest dump is younger than ~26 h.

If the host is managed (Render, Railway, Supabase, Neon, Heroku), its own
automated backups cover most of this — but confirm the **retention window** and
that you can trigger a restore yourself. Keep taking independent dumps anyway:
provider backups die with the provider account.

### Restoring

Restore into a **new, empty database first**, always. Never straight over a live
one — if the dump turns out to be short, you have destroyed the only copy.

```bash
# 1. a scratch target
createdb -h "$DATABASE_HOST" -U "$DATABASE_USERNAME" kailo_restore_test

# 2. restore into it
pg_restore -h "$DATABASE_HOST" -U "$DATABASE_USERNAME" \
           -d kailo_restore_test --no-owner --no-privileges \
           kailo-20260802.dump

# 3. prove it before you trust it
psql -h "$DATABASE_HOST" -U "$DATABASE_USERNAME" -d kailo_restore_test -c "
  select 'products', count(*) from products
  union all select 'categories', count(*) from categories
  union all select 'gallery_images', count(*) from gallery_images
  union all select 'files', count(*) from files
  union all select 'admin_users', count(*) from admin_users;"

# 4. only then, cut over — stop Strapi first
dropdb   -h "$DATABASE_HOST" -U "$DATABASE_USERNAME" kailo
createdb -h "$DATABASE_HOST" -U "$DATABASE_USERNAME" kailo
pg_restore -h "$DATABASE_HOST" -U "$DATABASE_USERNAME" -d kailo \
           --no-owner --no-privileges kailo-20260802.dump

# 5. tidy up
dropdb -h "$DATABASE_HOST" -U "$DATABASE_USERNAME" kailo_restore_test
```

`--no-owner --no-privileges` matters when the restore target's role differs from
the source's — the usual case between environments.

**Counts to expect.** Strapi 5 stores a draft *and* a published row per entry, so
a healthy database shows roughly double what the admin panel lists: 6 products
appear as 12 rows, 3 categories as 6, 30 gallery images as 60. A restore showing
*half* the expected rows is a draft/published mismatch, not a success.

**After a restore, before declaring victory:** boot Strapi and watch for
`[permissions] Public role: …` and `[permissions] public sign-ups disabled`.
Both reconcile on every boot from `src/seed/permissions.ts`, so a restored
database converges to the right API surface on its own — but seeing the lines
confirms bootstrap actually ran.

### Proof it works

Executed against the local PostgreSQL 17.10 instance on 2026-08-02, full cycle:

```

createdb kailo_restore_test

verification (source vs restored):

  ✓ contact_submissions  6   -> 6

  ✓ gallery_images      60   -> 60

  ✓ tables              72   -> 72
```

## Uploaded media

**On the local provider (the default), media is not in the database and is not in
git** — `.gitignore` excludes `public/uploads/*`. A database restore alone brings
back rows in `files` pointing at images that no longer exist, and the site renders
broken thumbnails while looking healthy.

So the local provider needs its own backup, taken *with* the dump so the two stay
consistent:

```bash
tar -czf "kailo-uploads-$(date +%Y%m%d).tar.gz" -C cms/public uploads
```

### The ephemeral-filesystem caveat

On Render, Railway, Fly, Heroku and any container host without a persistent
volume, `public/uploads` **does not survive a redeploy**. Not "might be slow to
restore" — the files are gone, every image on the site with them, on a routine
deploy that changed nothing else.

There is no backup schedule that fixes this; the fix is to stop storing media on
the instance. `config/plugins.ts` already carries the S3 and Cloudinary
providers behind an env switch — nothing but the provider package is missing:

```bash
npm install @strapi/provider-upload-aws-s3      # then UPLOAD_PROVIDER=aws-s3
# or
npm install @strapi/provider-upload-cloudinary  # then UPLOAD_PROVIDER=cloudinary
```

Naming a provider without its package fails at boot with the install command you
need, by design — see the README's "Switching the upload provider".

Once media is on a bucket, its backup becomes the bucket's: turn on **versioning**
and a lifecycle rule, and the tarball above is obsolete. Remember to add the
serving host to `CDN_URL` / `CDN_HOSTS` or the admin's media library fills with
broken thumbnails (the CSP in `config/middlewares.ts` is what blocks them).

**Migrating existing files:** copy `public/uploads` into the bucket preserving
file names, then re-point the `url` column in `files`. Strapi does not rewrite
those rows for you. Take a dump first.

## Rollback

### Storefront (container)

The storefront holds no state, so a rollback is only ever "run the previous
image". **Keep the tagged images — they are the rollback mechanism.** There is no
dashboard to promote from since Vercel was removed; if the only artefact is
`latest`, the fastest path back is a rebuild from the last good commit, which
costs minutes rather than seconds.

```bash
docker tag kailo-web:<good-sha> kailo-web:latest && docker compose up -d frontend
```

Revert the code afterwards, calmly, so the next build does not reintroduce the
fault.

Note the storefront pins nothing about the CMS at runtime *except* through
`VITE_STRAPI_URL`, which is inlined at build time. Changing it means a rebuild —
so an image is tied to one CMS origin, and rolling back to an image built against
a different one silently moves the site's data source.

### CMS (Strapi)

Strapi applies schema changes on boot, so a rollback has two halves and the order
matters:

1. **Take a dump of the broken state first.** You may need it to work out what
   happened, and to recover anything written since the last good backup.
2. **Roll the code back**, then restore the matching database dump — the one
   taken *before* the deploy you are undoing. Code and schema have to move
   together: older code against a newer schema is the failure mode that looks
   like a working app until an editor opens the wrong page.

Keep the last known-good release tagged so "roll the code back" is unambiguous:

```bash
git tag -a cms-2026-08-02 -m "known good before <change>"
git push origin cms-2026-08-02
```

### Seed and `SEED_VERSION`

`src/seed/index.ts` re-seeds when `SEED_VERSION` changes, and **a re-seed
overwrites editor changes** with the canonical values in `src/seed/data.ts`.
That is intended, and it is also a way to lose a week of copy edits.

- Take a dump before bumping `SEED_VERSION`.
- Set `SEED_ON_BOOT=false` once production content is being maintained by an
  editor rather than by the seed, and drive it deliberately with `npm run seed`.
- There is no down-migration. Recovering from an unwanted re-seed means restoring
  the dump.

### Recovery drill

Restoring is only proven if it has been done. **Once a quarter**, restore the
latest production dump into a scratch database, run the verification query above,
and boot Strapi against it. It takes ten minutes and it is the only thing that
distinguishes a backup from a file.

## Dependency posture

`cms` carries **33 transitive vulnerabilities** from `@strapi/strapi`
5.51.0 — 4 high, 24 moderate, 5 low, 0 critical.

**Do not run `npm audit fix --force` here.** npm's proposed remedy is
`@strapi/strapi` 5.36.0 — a *downgrade* of fifteen minor versions, flagged
`isSemVerMajor`. It would roll the CMS backwards to "fix" advisories whose ranges
are open-ended upward.

The forward path instead:

```bash
npm run upgrade:dry    # preview
npm run upgrade        # @strapi/upgrade latest
```

Watch for a Strapi release above 5.51.0 that clears the advisories, upgrade
forward, then re-gate CI's backend audit step from `critical` to `high` in
`.github/workflows/ci-cd.yml` and delete the note there.

**Current exposure is bounded**, which is why this is a watch item rather than an
incident: the admin panel sits behind authentication, the upload endpoints answer
`403` to the public role, and the public API surface is the read endpoints plus
three write paths that are validated, rate-limited and honeypotted. The high-
severity entries (`@strapi/upload`, `sharp`, `brace-expansion`) are not reachable
by an unauthenticated caller on this configuration.

`frontend` is at **0 vulnerabilities** and its CI audit gate blocks at
`high` — keep it that way.

## Operator housekeeping

### Clear the dead variables out of local `.env` files

`cms/.env` on the original development machine carries **19 variables
that no code reads** — left behind by features that were removed rather than
disabled:

```
WHATSAPP_ENABLED           EMAIL_ENABLED        CART_REMINDERS_ENABLED
WHATSAPP_API_VERSION       EMAIL_PROVIDER       CART_REMINDER_DELAYS_HOURS
WHATSAPP_PHONE_NUMBER_ID   EMAIL_FROM           SITE_URL
WHATSAPP_ACCESS_TOKEN      EMAIL_REPLY_TO       BRAND_NAME
WHATSAPP_TO                SMTP_HOST
WHATSAPP_TEMPLATE_NAME     SMTP_PORT
WHATSAPP_TEMPLATE_LANG     SMTP_USER
                           SMTP_PASS
```

The README says it plainly: *"Nothing is sent to anyone. There is no outbound
email and no WhatsApp integration… Both were removed rather than left disabled."*
`frontend/.env` likewise carries an unused `VITE_WHATSAPP_MODE`.

None of these are tracked by git, so nothing has leaked. **Delete them anyway.**
An empty `WHATSAPP_ACCESS_TOKEN=` sitting in a dotfile is an invitation to paste
a live Meta token into a variable nothing reads — a real credential, in a real
file, protecting nothing and rotated by nobody.

The tracked `.env.example` files advertise only variables the code actually
reads; they were checked and are clean.

### Secrets

Regenerate **every** secret per environment — `APP_KEYS`, `API_TOKEN_SALT`,
`ADMIN_JWT_SECRET`, `TRANSFER_TOKEN_SALT`, `JWT_SECRET`, `ENCRYPTION_KEY` and the
database credentials. Never promote a development value.

```bash
node -e "console.log(require('crypto').randomBytes(16).toString('base64'))"
```

Rotating `ENCRYPTION_KEY` on a populated database makes previously encrypted
values unreadable — treat it as a migration, not a config change, and dump first.
