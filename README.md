# Kailo

> *Crafted with finesse, made to move your soul.*

Storefront and headless CMS for **Kailo** — handmade ukulele bags, straps and
ukuleles. Two applications in one repository:

| | Package | Stack | Deploys to |
|---|---|---|---|
| **Storefront** | [`frontend/`](frontend/) | TanStack Start (React 19, Vite 7, Tailwind 4) rendered server-side via Nitro | Docker image, any container host |
| **CMS** | [`cms/`](cms/) | Strapi 5 (TypeScript) | Docker image + PostgreSQL |

There is no workspace tool. Each package has its own `package.json`,
`package-lock.json` and `.env`; install and run them separately.

---

## Repository layout

One folder per deployable, following the house structure:

```
Kailo/
├── .github/workflows/ci-cd.yml   type-check → lint → audit → build, both packages
├── docker-compose.yml            Postgres + the CMS + the storefront
├── .env.example                  compose's own vars — credentials and host ports
├── frontend/                     the storefront   → container (Dockerfile)
├── cms/                          Strapi 5         → container (Dockerfile)
├── infrastructure/db/            SQL run once, against an empty Postgres volume
└── docs/                         runbooks
```

One deliberate departure from that structure, and it is load-bearing:

- **There is no `backend/`.** Strapi *is* the backend — it serves the REST API
  the storefront reads, so a second service would have nothing to do. `cms/`
  carries the Dockerfile a backend folder otherwise would.

Both halves are containers, and there is no PaaS in the picture. The storefront
was on Vercel until it was removed: `frontend/vite.config.ts` now defaults to
Nitro's `node-server` preset, which builds a self-contained server under
`.output` that [`frontend/Dockerfile`](frontend/Dockerfile) runs. Nothing reads
`.vercel/output` any more, and a stale one from an older checkout is safe to
delete.

Three `.env` files, each with exactly one owner and none overlapping:

| | |
|---|---|
| `.env` | database credentials and host ports, read only by `docker-compose.yml` |
| `cms/.env` | Strapi's secrets, CORS, seeding, upload provider |
| `frontend/.env` | the storefront's build-time `VITE_` vars, for `npm run dev` and host builds |

`frontend/.env` is *not* read by the container — `.dockerignore` keeps it out of
the build context deliberately, since a workstation `VITE_STRAPI_URL` inlined
into an image points at a host that does not exist inside it. The image takes
that value from a build arg instead.

## The one thing to understand first

**The storefront runs in two modes, chosen by a single environment variable.**

```
VITE_STRAPI_URL unset   ->  snapshot mode  (how it is deployed today)
VITE_STRAPI_URL set     ->  live mode
```

**Snapshot mode** serves a committed copy of the CMS content from
[`src/lib/cms-snapshot/`](frontend/src/lib/cms-snapshot/) and the images in
`public/uploads/`. The site is then a pure function of the repo — it builds and
runs with no CMS, no database and no network. This is deliberate, not a
fallback, and it is how the site is deployed while the CMS is not yet hosted.

**Live mode** reads everything over the REST API instead. Setting the variable
is the only change required; no code differs between the two.

Two consequences worth knowing up front:

- `import.meta.env` is **inlined at build time**, so switching modes needs a
  rebuild, not just an env change. There is deliberately no localhost default —
  a forgotten variable would otherwise ship `http://localhost:1337` to
  production and 500 every route.
- The snapshot is regenerated by hand, against a running CMS:
  ```bash
  cd frontend && node scripts/snapshot-cms.mjs
  ```
  Re-run it whenever the seeded content changes, or the deployed site keeps
  serving the old copy.

## Quick start

Requires **Node 22** and, for the CMS, **PostgreSQL** (or Docker).

### Storefront only

Enough to see the site — no CMS, no database:

```bash
cd frontend
npm ci
npm run dev          # http://localhost:8080
```

With no `.env`, this runs in snapshot mode and every page renders real content.

### With the CMS

Everything in containers, from the repo root:

```bash
cp .env.example .env            # database credentials and host ports
cp cms/.env.example cms/.env    # then fill in the six secrets
docker compose up -d            # Postgres, the CMS on :1337/admin, the site on :8080
```

`cms/.env` must exist before the first `up` — compose reads it for the Strapi
secrets and stops with *"env file not found"* without it.

The `frontend` container is a production image with no autoreload, and it builds
in **snapshot mode** by default, so the site on :8080 serves the committed CMS
copy and does not talk to the `cms` container at all. That is the point: it runs
with nothing configured. Pointing it at a live CMS is a rebuild, not a restart,
and the URL has to resolve from both the container and the browser — the
`frontend` service in [`docker-compose.yml`](docker-compose.yml) spells out why.
While actually editing the storefront, use `npm run dev` instead.

Or run Strapi on the host with autoreload, and containerise only the database —
which is what you want while editing schemas:

```bash
docker compose up -d db         # or point DATABASE_* at your own Postgres
cd cms && npm ci && npm run develop
```

Strapi creates its tables, reconciles the Public role's permissions, and seeds
the full content set on a fresh database. Create the first admin user in the
panel — there is no default login.

Then point the storefront at it:

```bash
cd frontend
echo "VITE_STRAPI_URL=http://localhost:1337" > .env
npm run dev
```

Full setup, including hosted-Postgres options and the secret-generation
one-liner, is in the [CMS README](cms/README.md#quick-start).

> **Port 1337 note.** It is Strapi's convention and the committed default, but on
> some Windows machines Razer's `RzSDKServer` squats on it. If you hit *"The port
> 1337 is already used"*, set `PORT=1338` in `cms/.env` — and make
> `VITE_STRAPI_URL` match.

## Scripts

**`frontend`**

| | |
|---|---|
| `npm run dev` | dev server on :8080 |
| `npm run build` | production build to `.output` (Nitro `node-server`) |
| `npm run lint` / `npm run format` | ESLint / Prettier |
| `node scripts/snapshot-cms.mjs` | regenerate the CMS snapshot |

To smoke-test the real SSR output — the same bundle the image runs — build and
start it directly:

```bash
npm run build
node .output/server/index.mjs      # :3000, or set PORT
```

Note that `npm run build` inlines whatever `VITE_STRAPI_URL` your local `.env`
carries. If that points at a CMS you are not running, every content route
renders the error page; move the `.env` aside to check snapshot mode.

**`cms`**

| | |
|---|---|
| `npm run develop` | Strapi with autoreload + admin panel |
| `npm run build` / `npm start` | production build / run |
| `npm run seed` | re-run the content seed (idempotent) |
| `npm run media:optimize` | regenerate Media Library derivatives |
| `npm run upgrade:dry` | preview a Strapi upgrade |

## What's modelled

Ten content types in [`cms/src/api/`](cms/src/api/), defined
in code as `schema.json` and pre-seeded:

- **Catalogue** — `product`, `category` (Ukulele Bags, Ukulele Straps, Ukuleles), `gallery-image`
- **Page copy** — `home-page`, `about-page`, `contact-page`, `global`
- **Captures** — `contact-submission`, `newsletter-subscription`, `cart`

Eleven storefront routes: `/`, `/about`, `/products`, `/products/$id`,
`/gallery`, `/contact`, `/cart`, `/wishlist`, plus `/account`, `/login` and
`/checkout` as deliberate "coming soon" pages — there is no auth or commerce
phase yet.

The API contract between the two halves is
[`cms/INTEGRATION.md`](cms/INTEGRATION.md).

## Security posture

Worth knowing before changing anything public-facing:

- **The public API surface is defined in code**, not in the admin panel.
  [`src/seed/permissions.ts`](cms/src/seed/permissions.ts) reconciles
  the Public role on every boot and actively *revokes* anything it does not
  grant, so a permission ticked by hand does not silently persist.
- **Public sign-ups are forced off.** `POST /api/auth/local/register` is
  disabled on every boot; the switch lives in the database, not in a config
  file. Set `USERS_ALLOW_REGISTER=true` when an auth phase exists.
- **Carts cannot be enumerated.** `find` and `delete` are not merely denied —
  the routes are not declared, so `GET /api/carts` is a 404.
- **Both public forms** are honeypotted and per-IP rate-limited.
- The storefront sends `nosniff`, `X-Frame-Options`, `Referrer-Policy`,
  `Permissions-Policy` and HSTS. There is deliberately **no CSP** — TanStack
  Start inlines its hydration script, so a useful policy needs per-response
  nonces.

Never commit a `.env`. The tracked `.env.example` files document every variable
the code actually reads.

## CI

[`.github/workflows/ci-cd.yml`](.github/workflows/ci-cd.yml) runs on every PR and push
to `main`: `npm ci` → type-check → audit → build, for both packages (plus ESLint
on the frontend, which is the only half configured for it).

Two asymmetries, both intentional and commented in the workflow:

- The **frontend audit blocks at `high`** — it sits at zero vulnerabilities, so
  anything reaching that bar is new.
- The **backend audit blocks at `critical`** and reports `high` non-blocking. It
  carries 33 transitive advisories from `@strapi/strapi` 5.51.0 with no forward
  fix — `npm audit fix` proposes a *downgrade* to 5.36.0. Gating at `high` would
  make the pipeline permanently red and teach everyone to ignore it.

### Two gotchas that only bite on a fresh checkout

**1. Regenerate the frontend lockfile with npm 10, not 11.**

Node 22 bundles npm 10.9.x, and that is what CI *and the Docker build* use. npm
11 prunes two optional peer deps (`@emnapi/core`, `@emnapi/runtime`) that npm 10
requires, producing a lockfile npm 10 rejects outright. If you run `npm install`
or `npm audit fix` with npm 11 in `frontend`:

```bash
npx npm@10 install     # before committing
```

**2. The backend needs its types generated before type-checking.**

`types/generated/` is gitignored, so Strapi's `contentTypes.d.ts` and
`components.d.ts` exist on any machine that has run `strapi build` or `develop`,
and never on a clean clone. CI runs `npx strapi ts:generate-types` first; do the
same if `tsc` fails on a fresh checkout.

## Deploying

Both halves ship as container images, built by the Dockerfile in their own
folder. There is no PaaS and nothing auto-deploys — `docker compose up -d
--build` is the same operation locally and on a host.

**Storefront → any container host.** [`frontend/Dockerfile`](frontend/Dockerfile)
builds Nitro's `node-server` output and runs `node .output/server/index.mjs` on
:8080 as a non-root user. The runtime image carries no `node_modules` — Nitro
bundles its dependencies.

Set the CMS origin **at build time**, because vite inlines it:

```bash
docker build --build-arg VITE_STRAPI_URL=https://cms.example.com -t kailo-web ./frontend
```

Omit it for snapshot mode. Never pass `http://localhost:1337` — inside the
container that is the container.

**CMS → any container host + PostgreSQL.** [`cms/Dockerfile`](cms/Dockerfile)
builds and runs Strapi with `NODE_ENV=production` already set. Uploads go to a
named volume on the local provider; move them to S3/Cloudinary before running on
an ephemeral filesystem.

Before the first real deploy, work through
[**Going to production**](cms/README.md#going-to-production) — it
covers secrets, CORS, `PUBLIC_URL`, and switching uploads off local disk, which
does not survive a redeploy on an ephemeral filesystem.

Backups, restore, rollback and the dependency-upgrade posture:
[`docs/backup-recovery.md`](docs/backup-recovery.md).

## Known gaps

- **Auth, checkout and orders are not built.** `/login`, `/account` and
  `/checkout` are placeholder pages by design.
- **Nothing is emailed.** A contact submission is a row in the admin panel that
  someone answers by hand.
- **The cart is mirrored, not owned** — localStorage is the source of truth; the
  `cart` collection exists so a `?cart=<token>` link can rehydrate on another
  device. Anyone holding that token can read that cart.
- **The wishlist is client-side only.**
- Product imagery is still PNG (~37 MB of the deployed output); converting to
  WebP would cut roughly 34 MB.
